# Working Agreement — USA Olympic Weightlifting Scrape & Analysis

These rules govern how Claude should operate in this project. They apply to every session automatically.

## Operating Rules

1. **No drift.** Stick to the task the user actually asked for. If something adjacent looks broken or improvable, mention it briefly and ask before touching it — don't fix it as a side effect of the current task.
2. **Permission before code changes.** Never edit, create, or delete a file in this repo without stating the specific change first and getting a go-ahead. Exceptions only if the user explicitly says "just do it" / "go ahead without asking" for a given task.
3. **Limit token loss.**
   - Don't re-read files already read this session unless they may have changed.
   - Don't dump full CSV/notebook contents into context — sample, grep, or use pandas `.head()`/`.describe()` style checks instead.
   - `EDA/EDA.ipynb` is ~2.5MB — never read it in full; target specific cells or use `jq`/nbconvert to inspect.
   - `data/meet_results*.csv` are 300K+ rows — never cat the whole file; use `pandas`, `wc -l`, or `head`.
   - Prefer targeted Grep/Glob over broad exploration when the file is already known.
4. **Read back before announcing.** After making a change, re-open the diff/output and check it actually does what was claimed before telling the user it's done. Don't report success from intent alone.
5. **No pull requests.** The user edits everything themselves and merges branches locally or on the GitHub website. Never open, draft, or suggest a PR (no `gh pr`, no "create a pull request" links or offers) — commit on the working branch, and push only when asked. Merges to `main` are the user's call.

## Project Snapshot

- **Goals:** a personal passion and portfolio project — the user loves weightlifting and wants work that is genuinely stimulating. Success is a few hundred people using the site (stated 2026-11-07), so effort should stay proportionate: shipping and getting real feedback matters more than piling on features.
- **Pipeline:** `scraper/meet_scraper.py` (Playwright, logs into USAW portal, handles 2FA, scrapes meet results, appends new rows to `data/meet_results.csv`, deduped on `(Meet, Date, Name, Bodyweight)` with format-aware date normalization — see note below; date range for each run comes from `get_scrape_date_range()`, a fixed window of the last 3 months up to today) → `transform/meet_clean.py` (parses `Weight Category` into age group/gender/bodyweight class, drops duplicates, removes physiologically-impossible outliers, converts missed lifts to NaN + miss flags, flags bomb-outs via a `bombed_out` column instead of deleting them; known data-entry errors fixed by content match, not row index; full rebuild each run, writes `data/meet_results_CLEANED.csv`) → `transform/feature_engineering.py` (24 leakage-safe rolling/expanding features per athlete — performance-history ones computed on non-bomb-out rows only, attendance ones over every row, bomb-out rows themselves get NaN performance features — plus `weight_class`/`performance_percentile` (ranked among non-bomb-outs only) — the latter two are shared by the notebook's segmented analysis and `models/evaluate.py`, single source of truth; reads the cleaned CSV, writes `data/meet_results_FEATURES.csv`) → `models/train.py` (LR, RF, XGBoost baseline + tuned; `train_all(df)` returns fitted models + train/test splits for reuse) → `models/evaluate.py` (segment-aware MAE breakdown + residual plot; fixed a scale bug from the original notebook — see below) → `EDA/EDA.ipynb` (now ends after the segmented-analysis-setup section; modeling/evaluation/write-up cells removed, extracted to the files above) → `docs/findings.md` (Key Findings/Error Analysis/Limitations/Future Work, moved verbatim from the notebook, plus the NN post-mortem kept as historical record). Project is CSV-only for the scrape/clean/model pipeline — Supabase was removed from that role (2026-08-06). It's come back in a different, narrower role: as the website's read-only serving database (Phase 2), populated by `transform/load_to_supabase.py` — not part of the scraper's own storage/dedup logic, which stays CSV-only. See `ROADMAP.md` Phase 2.
- **Data:** `data/meet_results.csv` (raw, ~325K unique rows) → `data/meet_results_CLEANED.csv` (324,984 rows after cleaning, 20,717 flagged `bombed_out`) → `data/meet_results_FEATURES.csv` (same rows, plus 24 leakage-safe features + `weight_class` + `performance_percentile`; bomb-out rows have NaN performance features/percentile; `models/train.py` excludes them). Both rebuilt locally 2026-09-29; the local CSVs are only as fresh as the last local rebuild (CI rebuilds them but doesn't commit them back, so the tracked `CLEANED.csv` in git is stale too). The live Supabase table is the current copy: 329,914 rows, 20,895 bomb-outs, data through 2026-11-01 (2026-11-07). `meet_results_FEATURES.csv` is ~118MB, over GitHub's 100MB per-file push limit, so it is gitignored and local-only (CI regenerates it; training reads a locally rebuilt copy) — **back it up before switching to a branch that still tracks it** (older history does): the checkout overwrites or deletes the local file, which already happened once. No unique athlete ID — athletes are grouped by name only (known limitation).
- **Models:** Linear Regression, Random Forest, XGBoost, CatBoost, LightGBM (all baseline; XGBoost/LightGBM/CatBoost also tuned via `RandomizedSearchCV`) in `models/train.py`. Ensembling the three tuned tree models gives a modest MAE improvement (10.01kg vs XGBoost alone at 10.04kg) — see `ROADMAP.md` for the full story, including the ElasticNet/StandardScaler experiment that was tried and removed, and the XGBoost+RF ensemble that came out worse and was also removed. `tune_lightgbm_quantiles()` trains/tunes 4 LightGBM quantile models (25th/50th/75th/99th, pinball-loss scored) and saves them to `models/saved/` via `joblib` — groundwork for the website's confidence-interval feature. Neural Network dropped entirely (Python 3.12/tensorflow incompatibility, never fixed); the saved `best_nn_model.h5`/`.keras` artifacts were deleted since nothing references them anymore. **Leakage fix (2026-09-30):** `FEATURE_COLS` no longer includes the current meet's own six `Sn#N_missed`/`CJ#N_missed` flags (only knowable after the meet, so leakage for a pre-meet prediction) — now 24 features, all prior-history or known pre-meet. Cost ~0.26kg (baseline XGBoost 9.98→10.24kg, fixed params, 57,714-row test set) — so the 10.01/10.04kg figures above predate the fix; re-run 2026-09-30 (57,714 test rows): tuned XGBoost 10.21, LightGBM 10.21, CatBoost 10.34, 3-model ensemble 10.18kg; segment MAE (tuned XGBoost) bottom-50th 11.58 / 50-85th 9.04 / top-15th 9.26kg. README updated with these. By athlete history (baseline XGBoost, one-off test, deliberately not in the pipeline): returning athletes 7.11kg vs 8.16kg for a naive "same as last meet" guess; first-time athletes ~27.8kg (the real use case always has ≥1 prior meet). Quantile models retrained on the 24-feature set (coverage 27.3/52.0/76.3/98.9% vs. 25/50/75/99% targets). LightGBM rewrites spaces in feature names, so the API must pass features positionally in `FEATURE_COLS` order.
- **Known bug fixed during extraction:** the notebook's segment-aware evaluation compared `performance_percentile` (a 0-100 scale) against 0.5/0.85 thresholds, so "top 15%" actually covered nearly the whole test set. Fixed in `models/evaluate.py` (uses 50/85). Corrected XGBoost segment MAE: bottom-50th 11.47kg, top-15th 8.91kg (~1.3x gap) — much more modest than the original (buggy) figures still recorded in `docs/findings.md` (52.36kg vs 9.76kg, ~5.5x gap), now replaced with the corrected figures (2026-11-07); the old ones sit in a "Historical Figures" section at the end.
- **Bomb-outs are flagged, not deleted (fixed 2026-09-30).** `meet_clean.py` no longer drops `Total <= 0` rows (20,717 of ~325K, ~6.4%); it adds a `bombed_out` boolean instead, so `CLEANED`/`FEATURES`/Supabase carry the complete record. `feature_engineering.py` computes every performance-history feature (bests, trends, miss rates, `Last Comp Total`, …) on non-bomb-out rows only — verified identical to the pre-change values on all 304,267 real rows — so a Total=0 never reads as a collapse and an athlete's next real meet still sees their last real total; attendance features (`Num Competitions`, `Days Since Last Comp`, `comps_last_180_days`, `avg_days_between_comps`, `comp_timing_deviation`) count bomb-outs as meets attended (changes those 5 features on 5-23% of rows; MAE effect ~0.01kg). `models/train.py`'s `prepare_train_test` excludes bomb-outs. Bomb-out rows currently have NaN performance features — a future bomb-out predictor will need them computed. Supabase has since been reloaded with the flagged data (2026-10-06).
- **`transform/load_to_supabase.py`** — reads `meet_results_FEATURES.csv`, trims to 18 display-relevant columns (17 + `bombed_out`) (drops the 24 model-only engineered features and `performance_percentile`), renames to clean SQL identifiers, and does a transactional TRUNCATE + reload into a Supabase `meet_results` table — this is what the website (Phase 2) will query. Connects via Supabase's **Session Pooler** specifically (free IPv4 — the direct connection and Transaction Pooler both require IPv6 or a paid dedicated IPv4 address), reading `SUPABASE_DB_URL` from the environment. Wired into `.github/workflows/clean-data.yml` (runs on pushes to `main` that change `data/meet_results.csv`, or manually via workflow_dispatch) with `SUPABASE_DB_URL` as a GitHub Actions secret; confirmed working 2026-10-06 after pinning `sqlalchemy==2.0.52` (SQLAlchemy 2.1 made plain `postgresql://` default to the psycopg v3 driver, which CI doesn't install). Includes the `bombed_out` boolean (added via `ALTER TABLE … ADD COLUMN IF NOT EXISTS` before the truncate); the live table now holds the bomb-out-inclusive data (324,984 rows). **Backup:** before each truncate it copies the live table to `meet_results_backup` in the same transaction (`backup_live_table()`; skipped if the live table is empty), so the backup is always the previous run's data; `python transform/restore_from_backup.py` is the manual restore (dry run by default, `--confirm` to apply). `python tests/check_backup_restore.py` tests both against Supabase using temporary tables only. `python tests/smoke_deployed.py <url>` smoke-tests a running copy of the site (a Vercel preview/production URL or the local dev servers) over real HTTP. **Security (2026-11-07):** in Supabase every table in `public` is exposed through a REST API for the public `anon`/`authenticated` roles, and new tables get full privileges for them automatically. `db/website_access.sql` — run by the user on 2026-11-07; it sets a password, so Claude must never run it — turned on row-level security for `meet_results`, revoked those roles' access, and created the read-only `website_reader` login the website uses in production (its password was changed from the file's placeholder; the pipeline stays on the `postgres` login). `backup_live_table()` turns row-level security on for the backup table it creates, because new tables otherwise inherit the open access.
