# Roadmap — USA Olympic Weightlifting Scrape & Analysis

Working task list, refined 2026-08-06. Ordered: Phase 1 (pipeline/modeling) is meant to land before Phase 2 (website) starts, since the website features depend on clean, incrementally-updated data.

Do not start any item here without confirming scope in chat first — see `CLAUDE.md`.

## Phase 1 — Pipeline & Modeling Refactor

- [x] **Scraper: append instead of overwrite.** `meet_scraper.py` now appends new rows to `data/meet_results.csv`, deduped on `(Meet, Name, Bodyweight)` against existing rows, instead of regenerating the file each run. Supabase removed entirely — project is CSV-only.
- [x] **Scraper: data-integrity and reliability fixes.** A real scrape run showed far more "already in CSV" overlap than made sense, which led to finding and fixing three separate bugs: (1) the dedup key was missing Date, so recurring annual meets without a year in the name (e.g. "Bay State Games") could wrongly treat a returning athlete's new entry as a duplicate of an earlier year's and silently drop it — fixed by adding Date to the key. (2) `data/meet_results.csv` has a mix of date formats (original bulk-loaded historical data in `M/D/YYYY`, this scraper's own output in `YYYY-MM-DD`) that pandas' default parsing couldn't handle correctly, leaving `get_scrape_date_range()` permanently blind to the scraper's own prior progress (it kept recomputing the same stale starting point instead of advancing) — fixed with format-aware parsing (`parse_mixed_format_dates`/`normalize_date_key`) in both `meet_scraper.py` and `transform/meet_clean.py`; `get_scrape_date_range()` now reads the cleaned CSV (single canonical date format) with a raw-file fallback. (3) Both pagination loops (meet listing, athlete tables within a meet) were waiting a blind fixed second instead of confirming content actually changed — fixed to wait for real content-signature changes — and a per-meet try/except now logs and skips a single bad meet (e.g. a phantom last-page row, or a site test/admin event) instead of crashing and losing the entire scrape. **Operational note:** `RECOVERY_MODE = True` is currently active in `meet_scraper.py` — a one-time override re-scraping January 2025-present to recover data affected by bugs (1)/(2). Set back to `False` once that run is confirmed complete, to resume normal incremental operation via `get_scrape_date_range()`.
- [x] **Cleaner + feature engineering: own files.** `transform/meet_clean.py` now combines Weight Category parsing with the notebook's outlier/miss cleaning (the two hardcoded-index data fixes rewritten as content-based matches so they survive future appends). `transform/feature_engineering.py` extracts the notebook's 24 leakage-safe rolling/expanding features, plus `weight_class`/`performance_percentile` (added later, once `models/evaluate.py` needed them too — single source of truth instead of duplicated logic). Revised from the original "append-based" plan to a full rebuild each run instead — feature engineering needs each athlete's complete history to compute correctly, and a full recompute over ~282K rows is cheap enough (cleaning: seconds; feature engineering: ~12 min, dominated by per-athlete rolling calculations). Verified against real data.
- [x] **Modeling: extract to its own files.** `models/train.py` (Linear Regression, Random Forest, XGBoost baseline + tuned) and `models/evaluate.py` (segment-aware MAE breakdown + residual plot). Neural Network dropped entirely rather than extracted — see `docs/findings.md` for the historical reasoning, `CLAUDE.md` for current model status. Found and fixed a real bug while extracting `evaluate.py`: the notebook compared a 0-100 scale `performance_percentile` against 0.5/0.85 thresholds, so "top 15%" covered nearly the whole test set — corrected to 50/85. Both files verified against real data (results in `CLAUDE.md`). `EDA.ipynb` now ends after the segmented-analysis-setup section; all modeling/evaluation/write-up cells removed.
- [x] **Add models:** CatBoost and LightGBM added to `models/train.py` (baseline + tuned, matching the existing XGBoost `RandomizedSearchCV` pattern). ElasticNet was also added and tested (including with `StandardScaler`, since it's the one model in the lineup actually sensitive to feature scale) but only showed a slight improvement, nowhere near the tree-based models' ~10kg MAE range — both ElasticNet and the scaling step were removed rather than carry the added complexity for a model unlikely to be used. Ensembling the three tuned tree models (XGBoost + LightGBM + CatBoost) gave a small improvement (10.01kg vs XGBoost alone at 10.04kg) — the models are correlated enough that ensembling has limited room to help. A follow-up XGBoost + Random Forest ensemble (testing whether a structurally different model adds more diversity) came out worse (10.15kg) and was removed.
- [x] **Notes/documentation: own file.** `docs/findings.md` — Key Findings, Error Analysis, Limitations and Bias, Future Work, plus the Neural Network post-mortem, moved verbatim from the notebook. Two dated caveat notes added where figures were affected by the NN removal / segment-threshold bug. User is doing a manual editing pass over this and the README before pushing to GitHub.
- [ ] **GitHub Actions — cleaner.** First attempt tried committing `meet_results_CLEANED.csv`/`meet_results_FEATURES.csv` back to git after each run — hit a hard wall: `FEATURES.csv` is 105.58MB, over GitHub's 100MB per-file push limit (rejected outright, not a warning). Investigated Git LFS as a fix; rejected — these files regenerate every run, and LFS storage accumulates *every version* pushed, not just the latest, so the free 1GB LFS tier would be exhausted within roughly 6-7 runs at this file size. **Revised plan, now built and confirmed working locally:** `transform/load_to_supabase.py` reads `meet_results_FEATURES.csv`, trims to 17 display-relevant columns (drops the 24 model-only engineered features, plus `performance_percentile` — deliberately excluded since it's derived from internal, non-official weight-class bins meant for modeling/analysis, not something to present as-is on the website), renames to clean SQL identifiers, and does a transactional TRUNCATE + reload into a Supabase `meet_results` table. Connection: direct Postgres via SQLAlchemy/psycopg2 (not Supabase's REST client, for efficient bulk loading), specifically through Supabase's **Session Pooler** — the direct connection is IPv6-only (or $4/mo for a dedicated IPv4 address), and the Transaction Pooler turned out to require the same IPv6/paid-IPv4 tradeoff; Session Pooler is the one mode with free IPv4, which is what resolved a `could not translate host name` DNS error hit during setup. Reads the connection string from `SUPABASE_DB_URL` (`.env` locally; will need a GitHub Actions secret for CI). **Wired into `.github/workflows/clean-data.yml`** — added a "Load data into Supabase" step (`SUPABASE_DB_URL` read from a GitHub Actions secret) and removed the old commit-CSVs-back-to-git step, since it's now redundant with the Supabase load and `meet_results_FEATURES.csv` (~96MB, growing) was creeping toward GitHub's 100MB push limit anyway. **Not yet confirmed end-to-end in CI** — pending a real test: user is running `meet_scraper.py` locally first, then pushing to trigger the updated Action, once back on stable wifi (currently on spotty connection). Also still open: the data being loaded is currently missing all bomb-out entries — see the bomb-outs item below. Model training stays intentionally decoupled from this pipeline — local, occasional, reads a locally-regenerated full `meet_results_FEATURES.csv`, not the trimmed production table.

  Also surfaced and fixed a real bug in the process: `requirements.txt` (new) had `pandas` unpinned, and GitHub Actions installed a newer version than what's been used locally throughout this project — it handled `.astype(str)` on NaN values differently, crashing `transform/meet_clean.py` in CI (`TypeError: expected string or bytes-like object, got 'float'`) despite working fine locally. Fixed with a defensive `isinstance(x, str)` check plus pinning `pandas==2.2.2` in `requirements.txt`.
- [ ] **Bomb-outs are currently deleted, not just excluded from modeling — needs fixing before the website/Supabase pipeline is truly complete.** Discovered while reasoning through athlete lookups: `transform/meet_clean.py`'s `df_cleaned = df_cleaned[df_cleaned["Total"] > 0]` filter removes every bomb-out row (Total ≤ 0, e.g. missing all 3 snatch or all 3 C&J attempts) — confirmed 21,732 rows (~6.3% of raw data) get dropped this way; 0 remain in `meet_results_CLEANED.csv`. This was a deliberate, documented choice (see README/`docs/findings.md` Limitations) made for modeling reasons — a `Total=0` isn't a weak performance, it's a qualitatively different event, and including it as a regression target would corrupt a model trained to predict total. That reasoning is sound *for modeling*, but the filter currently lives in `meet_clean.py`, which is shared by everything downstream — including the website and the already-roadmapped "Bomb out rates and prediction" feature (Phase 2 below), which is **currently impossible to build**, since the data it needs is deleted three files upstream, before it's ever counted. **Proposed fix:** move the exclusion out of `meet_clean.py` (which should represent the complete, true historical record) and into `models/train.py`'s data-prep step instead, so `meet_results_CLEANED.csv`/`FEATURES.csv`/Supabase all stay complete. Real complication: `feature_engineering.py`'s trend-based features (`total_trend_last_3`, `improvement_streak`, `sn`/`cj_improvement_last_3`) would need bomb-out rows treated as excluded/NaN specifically for those calculations (same pattern as individual missed-lift handling), since a bomb-out would otherwise look like a catastrophic real decline rather than a missed attempt — while attendance-based features (`Num Competitions`, `Days Since Last Comp`, comp-frequency) should probably still count a bomb-out meet as a real competition attended. Would also want an explicit `bombed_out` boolean column so the website can display "DNF" rather than a bare `Total: 0`. Touches `meet_clean.py`, `feature_engineering.py`, `models/train.py`, and `load_to_supabase.py`'s schema — not yet started.
- [ ] **GitHub Actions — scraper (blocked/open investigation).** USAW's portal requires a 2FA code delivered by email/SMS each login — there's no way to generate that code programmatically, so full unattended automation isn't currently possible. Two paths, undecided:
  - Keep the scraper manual/local only (default/safe assumption for now).
  - Investigate whether USAW's login supports a "remember this device" session that outlives a single login — if so, a saved session/cookie could be stored as a GitHub secret and reused in Actions until it expires, needing periodic manual refresh. Unverified — needs someone to actually check the login flow before this is a real option.

## Phase 2 — Website

**Stack: data layer built and working, frontend still open.** Data layer is Supabase (Postgres) — the website will query it directly for lookups/comparisons rather than recomputing anything per-request. `transform/load_to_supabase.py` (see Phase 1's "GitHub Actions — cleaner" item for full detail) loads a trimmed 17-column subset of the cleaned data via a transactional TRUNCATE + reload, confirmed working locally through Supabase's Session Pooler (the one connection mode with free IPv4). Not yet wired into the actual GitHub Actions workflow — still a manual local script for now. Verified this comfortably fits Supabase's free tier for expected usage: ~35MB raw trimmed data today (282K rows, 62.7K distinct athletes, ~123 bytes/row), well under the 500MB storage limit even with Postgres/index overhead, and estimated egress in the low single-digit MB/month range against a 5GB limit — and since the load pattern is a full replace each run (not accumulating like Git LFS would have), push frequency doesn't affect either limit. **Known gap:** the data currently loaded is missing every bomb-out entry (see Phase 1's bomb-outs item) — athlete lookups will look incomplete until that's fixed. Frontend framework/hosting (Streamlit/Dash vs. a full separate frontend + API) still undecided.

Features (chunked out from "website idea"):

- [ ] **Athlete lookup** — search/view a specific athlete's history.
- [ ] **Meet lookup** — search/view a specific meet's results.
- [ ] **Graph of specific athletes** — performance over time for a chosen athlete.
- [ ] **Confidence intervals (25/50/75/99) of future performance** — projected performance bands, with checkboxes to toggle each band on/off. Open question: exclude bomb-outs from this projection, or include them? **Modeling groundwork done:** `models/train.py`'s `tune_lightgbm_quantiles()` trains and tunes 4 LightGBM quantile models (one per quantile, `RandomizedSearchCV` scored on pinball loss at each quantile's specific `alpha` — not MAE, which would optimize for the wrong objective for anything but the median), with an empirical coverage/calibration check printed after training, and saves all 4 to `models/saved/` via `joblib` so they don't need retraining to reuse. Still open: the website UI itself, and whether to extend beyond LightGBM-only — an XGBoost+CatBoost quantile ensemble was discussed but deprioritized, since the same correlated-models dynamic that capped point-prediction ensembling gains (see above) likely applies here too.
- [ ] **"Bomb out" rates and prediction** — historical bomb-out rate stats plus a predictive model for bomb-out likelihood.
- [ ] **Graph overlap for two athletes** — compare two athletes, either overlaid on one graph or side-by-side.
- [ ] **A-standards integration** — incorporate IWF/USAW "A standard" qualifying totals so the site can show, live, the best men's and women's athletes and their % to that standard.
