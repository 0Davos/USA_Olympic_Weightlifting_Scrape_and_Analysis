## Phase 1 — Pipeline & Modeling Refactor

- [x] **Scraper: append instead of overwrite.** `meet_scraper.py` now appends new rows to `data/meet_results.csv`, deduped on `(Meet, Name, Bodyweight)` against existing rows, instead of regenerating the file each run. Supabase removed entirely — project is CSV-only.
- [x] **Scraper: data-integrity and reliability fixes.** A real scrape run showed far more "already in CSV" overlap than made sense, which led to finding and fixing three separate bugs: (1) the dedup key was missing Date, so recurring annual meets without a year in the name (e.g. "Bay State Games") could wrongly treat a returning athlete's new entry as a duplicate of an earlier year's and silently drop it — fixed by adding Date to the key. (2) `data/meet_results.csv` has a mix of date formats (original bulk-loaded historical data in `M/D/YYYY`, this scraper's own output in `YYYY-MM-DD`) that pandas' default parsing couldn't handle correctly, leaving `get_scrape_date_range()` permanently blind to the scraper's own prior progress (it kept recomputing the same stale starting point instead of advancing) — fixed with format-aware parsing (`parse_mixed_format_dates`/`normalize_date_key`) in both `meet_scraper.py` and `transform/meet_clean.py`; `get_scrape_date_range()` now reads the cleaned CSV (single canonical date format) with a raw-file fallback. (3) Both pagination loops (meet listing, athlete tables within a meet) were waiting a blind fixed second instead of confirming content actually changed — fixed to wait for real content-signature changes — and a per-meet try/except now logs and skips a single bad meet (e.g. a phantom last-page row, or a site test/admin event) instead of crashing and losing the entire scrape. **Operational note (updated 2026-09-30):** the recovery run completed (data committed 2026-08-29) and `RECOVERY_MODE` is back to `False`. `get_scrape_date_range()` now also caps `most_recent` at today, since the source has future-dated rows (a multi-week online meet, "CT Summer Slam 2026", dated through 2026-10-12) that would otherwise push the start date past the end date.
- [x] **Cleaner + feature engineering: own files.** `transform/meet_clean.py` now combines Weight Category parsing with the notebook's outlier/miss cleaning (the two hardcoded-index data fixes rewritten as content-based matches so they survive future appends). `transform/feature_engineering.py` extracts the notebook's 24 leakage-safe rolling/expanding features, plus `weight_class`/`performance_percentile` (added later, once `models/evaluate.py` needed them too — single source of truth instead of duplicated logic). Revised from the original "append-based" plan to a full rebuild each run instead — feature engineering needs each athlete's complete history to compute correctly, and a full recompute over ~282K rows is cheap enough (cleaning: seconds; feature engineering: ~12 min, dominated by per-athlete rolling calculations). Verified against real data.
- [x] **Modeling: extract to its own files.** `models/train.py` (Linear Regression, Random Forest, XGBoost baseline + tuned) and `models/evaluate.py` (segment-aware MAE breakdown + residual plot). Neural Network dropped entirely rather than extracted — see `docs/findings.md` for the historical reasoning, `CLAUDE.md` for current model status. Found and fixed a real bug while extracting `evaluate.py`: the notebook compared a 0-100 scale `performance_percentile` against 0.5/0.85 thresholds, so "top 15%" covered nearly the whole test set — corrected to 50/85. Both files verified against real data (results in `CLAUDE.md`). `EDA.ipynb` now ends after the segmented-analysis-setup section; all modeling/evaluation/write-up cells removed.
- [x] **Add models:** CatBoost and LightGBM added to `models/train.py` (baseline + tuned, matching the existing XGBoost `RandomizedSearchCV` pattern). ElasticNet was also added and tested (including with `StandardScaler`, since it's the one model in the lineup actually sensitive to feature scale) but only showed a slight improvement, nowhere near the tree-based models' ~10kg MAE range — both ElasticNet and the scaling step were removed rather than carry the added complexity for a model unlikely to be used. Ensembling the three tuned tree models (XGBoost + LightGBM + CatBoost) gave a small improvement (10.01kg vs XGBoost alone at 10.04kg) — the models are correlated enough that ensembling has limited room to help. A follow-up XGBoost + Random Forest ensemble (testing whether a structurally different model adds more diversity) came out worse (10.15kg) and was removed.
- [x] **Notes/documentation: own file.** `docs/findings.md` — Key Findings, Error Analysis, Limitations and Bias, Future Work, plus the Neural Network post-mortem, moved verbatim from the notebook. Two dated caveat notes added where figures were affected by the NN removal / segment-threshold bug. User is doing a manual editing pass over this and the README before pushing to GitHub.
- [ ] **GitHub Actions — cleaner.** First attempt tried committing `meet_results_CLEANED.csv`/`meet_results_FEATURES.csv` back to git after each run — hit a hard wall: `FEATURES.csv` is 105.58MB, over GitHub's 100MB per-file push limit (rejected outright, not a warning). Investigated Git LFS as a fix; rejected — these files regenerate every run, and LFS storage accumulates *every version* pushed, not just the latest, so the free 1GB LFS tier would be exhausted within roughly 6-7 runs at this file size. **Revised plan, now built and confirmed working locally:** `transform/load_to_supabase.py` reads `meet_results_FEATURES.csv`, trims to 18 display-relevant columns (17 + `bombed_out`) (drops the 24 model-only engineered features, plus `performance_percentile` — deliberately excluded since it's derived from internal, non-official weight-class bins meant for modeling/analysis, not something to present as-is on the website), renames to clean SQL identifiers, and does a transactional TRUNCATE + reload into a Supabase `meet_results` table. Connection: direct Postgres via SQLAlchemy/psycopg2 (not Supabase's REST client, for efficient bulk loading), specifically through Supabase's **Session Pooler** — the direct connection is IPv6-only (or $4/mo for a dedicated IPv4 address), and the Transaction Pooler turned out to require the same IPv6/paid-IPv4 tradeoff; Session Pooler is the one mode with free IPv4, which is what resolved a `could not translate host name` DNS error hit during setup. Reads the connection string from `SUPABASE_DB_URL` (`.env` locally; will need a GitHub Actions secret for CI). **Wired into `.github/workflows/clean-data.yml`** — added a "Load data into Supabase" step (`SUPABASE_DB_URL` read from a GitHub Actions secret) and removed the old commit-CSVs-back-to-git step, since it's now redundant with the Supabase load and `meet_results_FEATURES.csv` (~96MB, growing) was creeping toward GitHub's 100MB push limit anyway. **Not yet confirmed end-to-end in CI** — pending a real test: user is running `meet_scraper.py` locally first, then pushing to trigger the updated Action, once back on stable wifi (currently on spotty connection). The load now includes a `bombed_out` column (see the bomb-outs item below) but has not been re-run against Supabase yet. Model training stays intentionally decoupled from this pipeline — local, occasional, reads a locally-regenerated full `meet_results_FEATURES.csv`, not the trimmed production table.

  Also surfaced and fixed a real bug in the process: `requirements.txt` (new) had `pandas` unpinned, and GitHub Actions installed a newer version than what's been used locally throughout this project — it handled `.astype(str)` on NaN values differently, crashing `transform/meet_clean.py` in CI (`TypeError: expected string or bytes-like object, got 'float'`) despite working fine locally. Fixed with a defensive `isinstance(x, str)` check plus pinning `pandas==2.2.2` in `requirements.txt`.
- [x] **Bomb-outs: flagged instead of deleted (done 2026-09-30).** `transform/meet_clean.py` used to drop every `Total <= 0` row (20,717 of ~325K, ~6.4%), which also removed the data from the website/Supabase pipeline and blocked the Phase 2 bomb-out-rate feature. That filter is gone: rows are kept with a `bombed_out` boolean. `feature_engineering.py` computes all performance-history features on non-bomb-out rows only (verified identical to the previous values on all 304,267 real rows — a bomb-out never leaks into a real row, and `Last Comp Total` still reads an athlete's last *real* total), while attendance features count a bomb-out as a meet attended (changes those 5 features on 5-23% of rows; MAE effect ~0.01kg). `performance_percentile` is ranked among real performances only. `models/train.py`'s `prepare_train_test` excludes bomb-outs, so the modeling target is unchanged. `load_to_supabase.py` adds a `bombed_out` column (`ALTER TABLE … ADD COLUMN IF NOT EXISTS` before the truncate). `data/*_CLEANED.csv`/`_FEATURES.csv` rebuilt locally. **Still open:** Supabase not yet reloaded (deliberately held); bomb-out rows have NaN performance features, which a future bomb-out predictor would need computed.
- [x] **Modeling: removed leakage from `FEATURE_COLS` (done 2026-09-30).** The list included the current meet's own six `Sn#N_missed`/`CJ#N_missed` flags — only knowable after the meet. Removed; now 24 features, all prior-history or known pre-meet. Cost ~0.26kg (baseline XGBoost 9.98→10.24kg), so earlier MAE figures elsewhere are slightly optimistic. One-off split test (not in the pipeline): returning athletes 7.11kg vs 8.16kg for a naive "same as last meet" guess; first-time athletes ~27.8kg. The four saved quantile models were retrained on the 24-feature set.

  - Investigate whether USAW's login supports a "remember this device" session that outlives a single login — if so, a saved session/cookie could be stored as a GitHub secret and reused in Actions until it expires, needing periodic manual refresh. ## Phase 3 — Website Architecture & Deployment

Decided 2026-09-17. This is the concrete infra Phase 2's features ship on. As of 2026-10-07 the MVP code is built (Next.js pages + FastAPI endpoints, tested locally against Supabase) but **nothing is deployed** — no Vercel project, domain, or production secrets exist yet. The bullets below are architecture decisions; the go-live checklist at the end of this section is the work needed to actually ship the MVP.

- **Frontend + backend, one platform:** Next.js frontend with a FastAPI backend, both deployed on Vercel (backend as Python serverless functions). Chosen over Streamlit specifically because Streamlit Community Cloud doesn't support custom domains, and its component styling reads as an internal dashboard rather than a polished, "own thing" site — which conflicted with the goal here. Vercel end-to-end (rather than splitting frontend on Vercel / backend on Render) was chosen to keep moving parts low — one dashboard, one deploy pipeline, custom domain attached in one place. **Not yet spike-tested:** need to confirm LightGBM's compiled binary dependency actually deploys cleanly under Vercel's Python serverless runtime before building further on this assumption — native deps occasionally have quirks in serverless environments.
- **Predictions: live inference, not precomputed.** The quantile models (`models/saved/*.pkl` — 4 files, ~9MB total) get loaded directly into the FastAPI backend and run on-demand per request, rather than precomputing predictions into Supabase ahead of time. Reasoning: predictions should reflect each athlete's latest data at lookup time; precomputing would mean recomputing for every athlete on every pipeline run (wasteful) or accepting stale numbers between runs. At ~9MB total model size and expected low traffic, on-demand inference has no real compute-cost downside here.
- **Two Supabase tables: one live, one rolling one-run-behind backup — no dev/prod split.** Reverses the earlier "single table is fine for now" call (see Phase 1's GitHub Actions item), but not into a dev/staging setup — code branching (`main` + feature branches) stays a purely git-level concern, with every deployment reading/writing the same live table regardless of branch. Instead, the second table exists purely for disaster recovery: right before each pipeline run truncates and reloads the live table with newly cleaned data, `load_to_supabase.py` first copies the live table's current contents into the backup table, overwriting whatever was there — the run happening at all is evidence the prior run's data was fine, so backup always holds the last known-good state, one run behind. If a run ever loads something broken, the pre-run data is still sitting untouched in backup. Trade-off worth being explicit about: this protects you *after* something breaks, not before — there's no isolated pre-production table catching a bad load before real users see it. Restore is manual: a script run by hand to copy backup → live when needed, not automated. **Not yet implemented:** `load_to_supabase.py` currently only knows about the one table; needs the backup-copy step added before its existing TRUNCATE + reload, plus a separate standalone manual restore script.
- **Domain: custom domain, registrar TBD between Namecheap and Cloudflare.** Common pattern worth deciding explicitly at setup time: register at Namecheap and delegate DNS to Cloudflare (or register directly at Cloudflare, which handles both), then point records at Vercel — if Cloudflare sits in front of Vercel, its proxy typically needs to be set to DNS-only (proxy off) rather than proxied, since Vercel handles its own SSL/CDN. Not yet registered.
- **Auth: none.** Public read-only site — confirmed no login/accounts needed.
